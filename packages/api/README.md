# OmniPath Parquet API

REST API for querying OmniPath's Parquet tables from a local artifact directory (including a read-only mounted directory), served by its DuckDB queries in [`omnipath_api/queries`](omnipath_api/queries). PostgreSQL input separately supports HTTPS.

## Validating rebuilt molecular outputs

From the repository root, validate freshly built resource versions without a
running API server:

```bash
PYTHONPATH=packages/api/src:packages/core/src:packages/build/src:packages/resolver/src \
  .venv/bin/python scripts/validate_molecular_outputs.py \
  --data-root /path/to/data --resources signor intact \
  --output /tmp/molecular-validation.json
```

Use `signor/VERSION` and `intact/VERSION` to select exact builds; a bare name
selects its latest available version. The validator checks actual Arrow types,
typed entity identity, relation endpoints, supported scalar gene references,
reusable product closure, evidence counts, and payload ownership. Independent
DuckDB baselines are compared with TestClient product/isoform filters, paired
evidence, gene navigation, and Parquet exports. Temporary links isolate each
selected resource and read its published and serving tables; the source
outputs are read only. The JSON report includes sizes, selected examples and
query timings. Missing biological cases are marked unavailable. Exports larger
than `--max-export-relations` (default 10,000) are also marked unavailable.
Exit status is nonzero when a check fails. These checks establish consistency
of the built output and API; they do not claim comparison to absent upstream
source records.

## Key Features

- **Embedded DuckDB queries** (`omnipath_api.queries`): Out-of-core columnar streaming, predicate pushdown, and dynamic facet aggregation. The clients answer search, relation export and entity details with SQL macros (`../query/sql`) that give the same answers.
- **REST API**: Native support for `/api/*` and SvelteKit `/app-api/*` proxy endpoints, with autogenerated OpenAPI.
- **Exports**: the relations of filters or entity and group keys (`POST /export`, up to 100,000) as Parquet.
- **Service status**: `GET /status` reports query slots in use and waiting, recent response times and coarse host load; the explorer header polls it.
- **Pinned releases**: `GET /api/releases` lists OmniPath versions. Add
  `?release=2026.09` or `X-OmniPath-Release: 2026.09` to data requests to use that
  release's exact resource versions. See [Versioning](../../VERSIONING.md).

Resource updates and PostgreSQL snapshots have separate schedules. The default
Latest view selects the newest published version of each Parquet resource,
including newly added resources. Optional named Parquet releases retain their
existing pins. PostgreSQL's monthly release does not set the API default,
constrain resource publication or trigger API refreshes.

The explorer UI lives in `../web`.

## Architecture

- **`queries`**: the API's queries over the serving root (`ParquetQueries`): inventory, query services and
  presentation adapters; the routes call its methods. See `omnipath_api/queries/README.md`. The
  clients' search, relation export and entity details are the SQL macros of `../query/sql`,
  which the client tests compare with these queries.
- **`routers`**: HTTP routes grouped by feature; common request/response adapters.
- **`jobs`**: Durable queue, separately supervised worker and build adapters.
- **`server`**: FastAPI app construction, middleware and lifespan (`/api/docs`, `/api/openapi.json`).
- **`models`**: Pydantic request/response schemas that drive the OpenAPI document.
- **`cli`**: CLI entrypoint to launch the server.

## Quick Start

```bash
# Start the DuckDB API server
uv run --frozen omnipath-api --host 127.0.0.1 --port 8085 --data-root data

# Run full stack (API + web explorer)
./run_all.sh
```

Open interactive API docs from the web app (**API Docs** in the sidebar) or directly at `http://127.0.0.1:8085/api/docs`.

## Serving tables

Each resource version is served from its published tables and four serving
tables written by the build: `entity_term` (search), `relation_endpoint` (a key's
relations), `entity_group` (gene, product and chemical groups) and `relation_facet`
(each distinct combination of the relation filter columns). They are part of the
resource version, so the API needs no separate index build; downloads contain only
the published tables. Lookups by key read each resource's files separately, so only
the matching row groups are read.

Facet results share concurrent identical requests and use an LRU cache limited to
128 entries and 32 MiB of encoded results. Cache keys include normalized parameters,
resource inventory, pinned release and taxonomy references. This encoded-size bound
is not a process RAM limit. Equal-ranked entity labels now use a deterministic
tie-breaker.

`POST /relations/scoped-facets` returns the relation filter options a selection
leaves, without counts: for each filter group, the values of the relations that the
scope (an entity selection, molecular forms) and the other groups' filters keep, most
relations first. A group's own filters do not narrow it, so choosing a value keeps
the others of its group listed. Without an entity selection the options come from the
resource versions' `relation_facet` tables (about 37,000 rows for the full release);
with one, from the selected relations grouped the same way.

It accepts optional `taxonomyLimit` (1–10,000) and `taxonomyQuery` (case-insensitive
name/ID substring). Other facets and selected taxonomy values remain included, also
selected values that no relation has. Omitting the limit returns every option. The UI
requests one extra option to determine whether to show **Load more**, then increases
its limit. Requests with different taxonomy pages reuse the same cached options. JSON
responses support gzip at both the direct API and the public web proxy; the proxy
avoids forwarding compressed-body headers after Node has decompressed a response.

## Explorer starting examples

The unfiltered entity explorer calls `GET /entities/examples` instead of an empty
search. It shows up to twelve familiar chemicals, human proteins and pathways,
under “Explore some examples,” with no alphabetical continuation. Search, source
scopes, other filters, selection scopes and grouped results retain normal queries.

The suggestion list is in `examples.py`. Exact matching candidates come only from
the selected release; unavailable suggestions are skipped. The small response is
cached in memory and atomically saved under `.presentation/examples-v1/`, keyed
by entity input fingerprints, editorial suggestions, release and taxonomy references.
A missing cache is prepared on demand; read-only data mounts use the memory cache.
The presentation cache is optional and does not contain the full entity catalog.

To warm the default page after deployment, request `/entities/examples` with
`X-OmniPath-Release: latest`. Named releases prepare their own pages on first use.

### Entity details and relationships

The explorer requests `GET /entities/{key}?includeRelationships=false` for entity
properties and identifiers. It loads `GET /entities/{key}/relationships?limit=50&offset=0`
only when the Relationships tab opens; `nextCursor` supplies the next offset.
Identifier pagination uses already loaded data. The original combined response
remains available with the default `includeRelationships=true` for API compatibility.

Relationship lookup first selects scalar keys and source filenames, then reads
full annotations only from the matching resource files. Source copies and typed
quantities are preserved. No shared index or resource rebuild is required.
Entity responses and relationship pages have separate bounded memory caches
(32 MiB each), keyed by exact entity key, selected input fingerprints, release,
references and pagination. Concurrent identical requests share work; resource
updates invalidate results by selecting a new key. Opening the dialog does not
request the combined endpoint's unused interaction count or association list.

### Disable a resource for live queries

Set `disabled_resources` in `<data-root>/query_policy.json`, using inventory slugs:

```json
{"disabled_resources": ["rampdb"]}
```

The policy applies across releases and is read on query selection without a restart.
Default queries, details, facets and exports exclude these resources; explicitly
selecting a disabled resource returns HTTP 400. Catalog entries and resource file
downloads remain available, with `queryable: false` in the catalog. Remove the slug
to re-enable it. Publish policy changes with an atomic file replacement.

### Taxonomy names in the latest view

Named releases retain their immutable taxonomy subsets. The moving `latest` view
can use a complete offline NCBI name lookup, so newly added resources do not depend
on names collected for an older release. Prepare it from the cached
`data/references/taxonomy/taxdump.tar.gz` with:

```sh
uv run --frozen python -m omnipath_core.taxonomy_lookup --data-root data
```

This streams scientific/common names and merged IDs into a content-addressed
SQLite reference and atomically updates `latest-names.json`. Requests perform
indexed read-only lookups with a bounded name cache, without loading the whole
reference into memory or contacting NCBI. Common names take precedence over
scientific names; merged IDs keep their original identity. Re-run after updating
the NCBI archive. The lookup version participates in example, detail and facet
cache keys. Without a prepared lookup, the previous latest-release subset is
used. Unknown IDs remain explicitly labelled as NCBI taxon IDs.

## Administration and the build worker

Serving defaults to `OMNIPATH_READ_ONLY=true`. Every `/admin/*` endpoint requires
`OMNIPATH_ADMIN_SECRET` (or the legacy `OMNIPATH_ADMIN_PASSWORD`); no configured
secret disables administration. Supply the secret using `X-Admin-Secret` or the
admin cookie. Secrets in query strings are rejected. Mutations additionally require
`OMNIPATH_READ_ONLY=false` and a writable data mount.

The API persists submitted jobs in `<data-root>/jobs/queue.sqlite3`. It never
starts build threads. Run the supervised worker separately with the build
package and its dependencies installed:

```sh
uv run --frozen python -m omnipath_api.jobs.worker --data-root data
```

Use `--once` to process at most one queued job. Multiple API processes share the
transactional single-flight queue; an OS-owned lock permits one worker per data
root and is released on process death. Queued work survives API/worker restarts.
A worker interrupted during execution is recorded as failed on worker restart,
with an explicit instruction to inspect its outputs before retrying. This avoids
automatically repeating partially completed external work. SIGTERM/SIGINT request
cooperative cancellation before the worker exits. Progress, cancellation and final
results are durable. Persistence failures propagate and are logged.

Worker capability/source metadata is published in the queue so an API installation
without build dependencies can expose available worker operations. The metadata
reports installed capabilities, not worker liveness. Run the worker under a process
supervisor. The SQLite queue must be on a local filesystem shared by these
processes, not independently copied between replicas.

## Pagination and query contracts

Entity continuation cursors contain the complete relevance/label/identity ordering
and the chosen search phase. Treat `nextCursor` as opaque and return it unchanged
with the same query, filters and resources. A cursor from another query is rejected.

`GET /ontology/children` accepts `termId`, `ontologyId`, `limit` (1–1000) and `offset`.
Its response includes `total` and an integer `nextCursor`, or null at the end.
Namespace-qualified `namespace|identifier` terms and exact entity keys are accepted;
ambiguous labels/identifiers require qualification. Trees and children stay within
the resolved namespace. Tree seed nodes expose `hasMoreChildren`/`nextCursor` when
their initial child page is incomplete.

Historical filter names are normalized once by `SearchFilters`. Entity filters are
resolved identically for relation search, facets and export. A supplied filter that
matches no entities yields no rows; a short accession is resolved as an identifier.

Inventory discovery builds a complete immutable snapshot before publishing it in
one replacement. Every query in an HTTP request uses that same snapshot.
Read-only serving creates neither example cache files nor queue files. DuckDB connections use the shared connection
factory and close when the application lifespan ends.

## Query resource budget

HTTP queries lease a database from one bounded pool, including inventory refresh,
facets and export generation. Defaults are two concurrent queries, two DuckDB
threads and 1 GB per database. Configure `OMNIPATH_QUERY_CONCURRENCY`,
`OMNIPATH_DUCKDB_THREADS`, `OMNIPATH_DUCKDB_MEMORY_LIMIT` and
`OMNIPATH_QUERY_WAIT_SECONDS` (30 seconds by default). Requests that cannot
obtain a slot return 503 with `Retry-After: 1`. Idle databases are reused; stale
inventory generations close their databases without accumulating closed handles.

These limits apply per API process. DuckDB memory limits do not cover all Python,
Arrow or export buffers. Compose defaults to a 4 GB, four-CPU container as a
backstop; change its `API_*` budget variables together for the workload. Direct
Python callers should wrap concurrent operations in `queries.query_scope()`.
Use representative concurrent searches, facets and exports when sizing a deployment.

## Gene references and molecular evidence

Entity summaries expose `referenceEntityKey` and `geneReferenceKeys` separately
from `entityPk`. The record key and main `entityType` remain source typed.
`POST /entities/groups` accepts `strategy: "auto"` to apply gene-reference and
chemical-connectivity grouping together. Explicit strategies remain available
for API clients; group summaries
include `memberEntityTypes` and typed member keys. Missing references remain
separate records. Only supported `entrez:` scalar references form gene groups;
native fallback references and ambiguous catalogue gene links stay separate.
Source type filters apply to the members before grouping.

Relation summaries expose `subjectReferenceEntityKey` and
`objectReferenceEntityKey`. `SearchFilters.reference_entity_keys` browses the
shared gene references. `protein_entity_keys`, `transcript_entity_keys` and
`isoform_identifiers` select exact molecular context; `molecular_endpoint_mode`
is `any`, `source`, `target` or `both`. All identity constraints must match the
same endpoint in the same evidence occurrence. Filtered evidence and exports
retain only matching occurrences, with their paired subject/object forms.
`GET /relations/{key}/evidence` accepts these filters as a JSON query parameter
and collects evidence across all selected resource files with stable occurrence
keys. Entity details count standalone evidence (`molecularEvidenceTotal`); the items
are paged from `GET /entities/{key}/evidence`.

`GET /entities/{key}/molecular-context` separates catalogue-linked products from
observed forms and matching relations. A `gene:entrez:ID` group opens the gene
view; a reusable product key selects evidence explicitly naming that product.
`isoform_identifier=uniprot:P04637-2` selects that exact reported isoform.
Forms and standalone observations are paged; `observedForms` describes the
current relation page. Missing molecular fields stay unspecified.

Filtered exports return one row per relation with its annotations and evidence
as lists (only matching occurrences under a molecular form filter) and add
`referenced_product_records`, containing reusable product records needed to
interpret the selected forms. Serving never rewrites resource Parquets.
